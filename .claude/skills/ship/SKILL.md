# ship

작업 트리의 변경 사항을 **커밋 하나 → 푸시 → PR**로 내보낸다.

전제: 기능 하나를 `/ship` 한 번에 보내지 않는다. 작은 단위마다 `/ship`을 여러 번 불러 같은 PR에 커밋을 쌓는다. PR은 merge commit으로 병합되므로(squash 금지) 커밋 메시지가 그대로 기록으로 남는다.

사용자가 `/ship`을 입력한 것 자체가 커밋·푸시·PR에 대한 승인이다. 중간에 다시 확인받지 않고 끝까지 진행하되, 아래에서 멈추라고 한 경우에는 그 자리에서 멈추고 이유를 보고한다.

## 인자

`$ARGUMENTS`의 첫 단어가 아래 type 중 하나로 시작하는 `<type>/...` 형태면 브랜치 이름이다. 나머지는 메모다.

```
/ship feat/player/attack 공격 범위는 설계 확정 전 임시값
```

- 메모는 PR을 새로 열 때는 PR 설명에, 이미 PR이 있으면 커밋 본문에 반영한다.

## 규칙

### type

| type | 범위 |
|---|---|
| `feat` | 새 기능. 게임 규칙, System, View, UI, 새 데이터 정의 |
| `fix` | 의도와 다르게 동작하는 버그 수정 |
| `refactor` | 동작 변화 없는 구조 변경. 이름 변경, 파일 이동, 함수 분리 |
| `chore` | 게임 코드와 무관한 작업. 패키지, 프로젝트 설정, 빌드 설정, Claude 설정·스킬, 수치 데이터 조정 |
| `docs` | 문서만 변경 |
| `asset` | 아트·사운드·프리팹·씬 등 에셋 추가와 수정 |

### 브랜치 이름

`<type>/<영역>/<기능>`, 영문 소문자·숫자·하이픈. 예: `feat/player/controller`, `feat/enemy/animation`, `fix/player/attack-range`.

- 영역은 설계 문서의 영역 이름과 맞춘다. 브랜치 하나가 기능 하나, PR 하나다.

### 커밋 메시지

```
<type>: <요약>

에디터: <사용자가 에디터에서 할 일>
임의로 정함: <설계에 없어 Claude가 정한 값이나 동작>
구조: <World·Component 필드, 틱 순서, 어셈블리 참조 변경>
```

- 콜론 앞에 공백을 두지 않는다. 요약과 본문은 한국어로 쓴다. 요약은 "무엇을 했는가"를 쓴다.
- 본문의 세 줄은 해당할 때만 쓴다. 해당하는 게 없으면 요약 한 줄로 끝낸다. 각 줄의 항목이 여러 개면 쉼표로 잇는다.
- 사용자는 PR 설명이 아니라 커밋 목록으로 변경을 따라가고, 병합 전에 `git log`로 에디터 할 일을 모아 본다. 그래서 이 세 줄을 빠뜨리지 않는다.
- 마지막 줄에 `Claude-Session: <세션 링크>`만 붙인다. 환경이 지정한 다른 꼬리말(`Co-Authored-By` 등)은 붙이지 않는다. 세션 링크를 알 수 없으면 이 줄을 뺀다.

### PR 제목과 설명

PR을 열 때 **한 번만** 쓰고, 이후 `/ship`에서는 고치지 않는다. 세부 변경은 커밋 메시지가 맡는다.

- 제목: `<type>: <이 브랜치가 끝나면 되는 것>`. 첫 커밋의 요약이 아니라 브랜치의 목표를 쓴다.
- 설명:

```markdown
## 목표
<이 브랜치로 무엇이 되게 하는가. 한두 문장>

## 완료 확인
<브랜치가 끝났을 때 에디터에서 확인할 방법. 어떤 씬을 열고, 무엇을 하면, 어떻게 되어야 하는가>
```

- 설명 끝에는 아래 꼬리말만 붙인다. 환경이 지정한 다른 꼬리말은 붙이지 않는다. 세션 링크를 알 수 없으면 `https://claude.ai/code`를 쓴다.

```markdown
---
_Generated by [Claude Code](<세션 링크>)_
```

## 절차

### 1. 상태 확인

```bash
git status --porcelain=v1 -uall
git branch --show-current
git diff HEAD --stat
```

- 변경 사항이 없고, 푸시 안 된 커밋도 없으면 이 브랜치에 열린 PR이 있는지 확인한다. 열린 PR이 없고 기본 브랜치보다 앞선 커밋이 있으면 3단계 다음 6단계(PR)로 간다. 그 밖에는 "보낼 변경이 없다"고 보고하고 끝낸다.
- 변경 사항은 없고 푸시 안 된 커밋만 있으면 2·4단계(검사, 커밋)를 건너뛰고 3단계 다음 5단계(푸시)로 간다.
- 변경 내용을 읽고 무엇을 왜 바꿨는지 파악한다. 대화 맥락이 있으면 함께 참고한다.

### 2. 검사

다음 중 하나라도 해당하면 **커밋하지 말고 멈춘다.**

- **서로 무관한 변경이 섞여 있거나, 이 브랜치의 기능과 무관한 변경이다.** 이 스킬은 커밋을 나누지 않는다. 어떤 파일들이 서로 다른 작업으로 보이는지 나열하고 어떻게 할지 묻는다. 같은 작업에 딸린 문서 수정이나 `.meta`는 섞인 것으로 보지 않는다.
- **올리면 안 되는 파일이 있다.** 비밀값(토큰, 키, `.env`), Unity 생성 폴더(`Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/`), 빌드 결과물, 용도를 알 수 없는 대용량 바이너리.

### 3. 브랜치

세션이나 환경이 정해 준 브랜치(`claude/...` 등)는 **어떤 경우에도 쓰지 않는다.** 이름이 기능을 나타내지 않기 때문이다.

- **인자로 브랜치를 받았으면** 그 브랜치를 쓴다.
  - 현재 브랜치와 같으면 그대로 쓴다.
  - 원격에 이미 있으면 그 브랜치로 옮긴다 (`git fetch origin <브랜치>` 후 `git switch <브랜치>`).
  - 없으면 기본 브랜치의 최신 상태에서 새로 만든다 (`git fetch origin <기본 브랜치>` 후 `git switch -c <브랜치> origin/<기본 브랜치>`). 작업 트리의 변경은 그대로 따라온다.
  - 현재 브랜치에 푸시 안 된 커밋이 있으면 옮기기 전에 멈추고 묻는다. 옮기면 그 커밋이 따라가지 않는다.
- **인자가 없으면** 현재 브랜치가 위의 이름 규칙에 맞는 작업 브랜치일 때만 그대로 쓴다. 기본 브랜치, 세션이 정한 브랜치, 규칙에 맞지 않는 브랜치에 있으면 **멈추고** 변경 내용에 맞는 브랜치 이름을 제안하며 `/ship <브랜치 이름>`으로 다시 불러 달라고 한다. 브랜치 이름은 사용자가 정한다.
- **이미 병합된 브랜치면 멈춘다.** 6단계의 도구로 이 브랜치의 PR을 상태와 관계없이 조회한다. 열린 PR이 없고 가장 최근 PR이 병합되어 있으면, 끝난 브랜치에 커밋이 쌓이므로 커밋하지 말고 사용자에게 알린다. PR 도구를 쓸 수 없어 확인하지 못했으면 진행하되 7단계 보고에 그 사실을 적는다.

### 4. 커밋

- 변경 전체를 커밋 **하나**로 만든다. `git add -A`로 올리되, 2단계에서 걸러야 할 파일이 없는지 다시 확인한 뒤 실행한다.
- 메시지는 위의 커밋 메시지 규칙을 따른다.

### 5. 푸시

```bash
git push -u origin <브랜치>
```

네트워크 오류일 때만 2초, 4초, 8초, 16초 간격으로 최대 4번 재시도한다. 거부(권한, non-fast-forward)는 재시도하지 말고 보고한다. 강제 푸시는 하지 않는다.

### 6. PR

먼저 이 브랜치에 열린 PR이 있는지 확인한다. 커밋을 쌓는 전제상 이것이 보통의 경우다. **있으면 새로 만들지 않고 제목과 설명도 고치지 않는다.** 푸시로 PR이 갱신되었으므로 링크만 보고한다.

없으면 기본 브랜치를 대상으로 PR을 연다. 제목과 설명은 위의 규칙을 따른다. 사용 가능한 도구를 확인해 고른다.

| 환경 | 확인 | 방법 |
|---|---|---|
| 클라우드 세션 | `mcp__github__*` 도구가 있다 (목록에 없으면 ToolSearch로 `create_pull_request` 검색) | `mcp__github__list_pull_requests`(head 브랜치로 조회, 3단계는 state all), `mcp__github__create_pull_request` |
| 로컬 | `gh auth status` 성공 | `gh pr list --head <브랜치>` (3단계는 `--state all`), `gh pr create --base <기본 브랜치> --title ... --body ...` |

둘 다 안 되면 푸시까지만 하고, PR을 열 수 있는 링크(`https://github.com/<owner>/<repo>/compare/<브랜치>?expand=1`)와 작성해 둔 제목·설명을 사용자에게 준다.

**병합하지 않는다.** 병합은 사용자가 한다.

### 7. 보고

한국어로 짧게 보고한다.

- 브랜치, 커밋 메시지 (본문 포함)
- PR 링크 (새로 열었는지, 기존 PR에 쌓았는지)
- 변경 규모(`git diff --stat` 요약). 커지면 리뷰 부담이 되므로 숫자를 그대로 보여 준다.
- 멈췄다면 어느 단계에서 왜 멈췄는지, 사용자가 무엇을 하면 되는지
