# ship

작업 트리의 변경 사항을 **커밋 하나 → 푸시 → PR**로 내보낸다.

사용자가 `/ship`을 입력한 것 자체가 커밋·푸시·PR에 대한 승인이다. 중간에 다시 확인받지 않고 끝까지 진행하되, 아래 "멈추는 경우"에 해당하면 그 자리에서 멈추고 이유를 보고한다.

인자(`$ARGUMENTS`)가 있으면 PR 설명에 반영할 사용자 메모로 쓴다.

## 규칙은 CONVENTIONS.md에서 읽는다

커밋 type, 메시지 형식, 브랜치 이름, PR 설명 양식은 저장소 루트의 `CONVENTIONS.md`가 기준이다. 이 스킬에 규칙을 복사해 두지 않는 이유는, 규칙이 두 곳에 있으면 한쪽만 고쳐져 어긋나기 때문이다. 실행할 때마다 `CONVENTIONS.md`의 커밋·브랜치·PR 부분만 읽는다.

`CONVENTIONS.md`가 없거나 해당 내용이 없으면 `git log --oneline -20`의 기존 메시지 형식을 따르고, PR 설명은 "변경 내용 / 리뷰 포인트 / 확인 방법" 세 항목으로 쓴다.

## 절차

### 1. 상태 확인

```bash
git status --porcelain=v1 -uall
git branch --show-current
git diff HEAD --stat
```

- 변경 사항이 없고, 푸시 안 된 커밋도 없으면 "보낼 변경이 없다"고 보고하고 끝낸다.
- 변경 내용을 읽고 무엇을 왜 바꿨는지 파악한다. 대화 맥락이 있으면 함께 참고한다.

### 2. 검사

다음 중 하나라도 해당하면 **커밋하지 말고 멈춘다.**

- **서로 무관한 변경이 섞여 있다.** 이 스킬은 커밋을 나누지 않는다. 작업 단위를 처음부터 작게 유지하는 것이 전제다. 예를 들어 기능 코드와 무관한 설정 변경이 함께 있으면, 어떤 파일들이 서로 다른 작업으로 보이는지 나열하고 어떻게 할지 묻는다. 같은 작업에 딸린 문서 수정이나 `.meta`는 섞인 것으로 보지 않는다.
- **올리면 안 되는 파일이 있다.** 비밀값(토큰, 키, `.env`), Unity 생성 폴더(`Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/`), 빌드 결과물, 용도를 알 수 없는 대용량 바이너리.
- **`.meta` 짝이 맞지 않는다.** 아래 스크립트로 검사한다. 출력이 있으면 문제다.

```bash
bash .claude/skills/ship/scripts/check_meta.sh
```

`.meta`가 빠진 경우 Claude가 직접 만들지 않는다. GUID는 Unity 에디터가 만들어야 하므로, 사용자에게 에디터에서 프로젝트를 한 번 열어 달라고 안내한다.

### 3. 브랜치

- 세션 지시나 사용자가 지정한 브랜치가 있으면 그 브랜치를 쓴다.
- 이미 작업 브랜치(기본 브랜치가 아닌 브랜치)에 있으면 그대로 쓴다.
- 기본 브랜치(`main` 등)에 있으면 `CONVENTIONS.md`의 이름 규칙으로 새 브랜치를 만들어 옮긴다. 기본 브랜치에 직접 커밋하지 않는다.

### 4. 커밋

- 변경 전체를 커밋 **하나**로 만든다. `git add -A`로 올리되, 2단계에서 걸러야 할 파일이 없는지 다시 확인한 뒤 실행한다.
- 메시지는 `CONVENTIONS.md` 형식을 따르고 한국어로 쓴다. 요약은 "무엇을 했는가"를, 본문은 필요할 때만 "왜"를 쓴다.
- 환경이 커밋 메시지에 붙이라고 지정한 꼬리말이 있으면 붙인다.

### 5. 푸시

```bash
git push -u origin <브랜치>
```

네트워크 오류일 때만 2초, 4초, 8초, 16초 간격으로 최대 4번 재시도한다. 거부(권한, non-fast-forward)는 재시도하지 말고 보고한다. 강제 푸시는 하지 않는다.

### 6. PR

먼저 이 브랜치에 열린 PR이 있는지 확인한다. **있으면 새로 만들지 않는다.** 푸시로 PR이 갱신되었으므로 링크만 보고한다.

없으면 기본 브랜치를 대상으로 PR을 연다. 사용 가능한 도구를 확인해 고른다.

| 환경 | 확인 | 방법 |
|---|---|---|
| 클라우드 세션 | `mcp__github__*` 도구가 있다 (목록에 없으면 ToolSearch로 `create_pull_request` 검색) | `mcp__github__list_pull_requests`(head 브랜치로 기존 PR 확인), `mcp__github__create_pull_request` |
| 로컬 | `gh auth status` 성공 | `gh pr list --head <브랜치>`, `gh pr create --base <기본 브랜치> --title ... --body ...` |

둘 다 안 되면 푸시까지만 하고, PR을 열 수 있는 링크(`https://github.com/<owner>/<repo>/compare/<브랜치>?expand=1`)와 작성해 둔 제목·설명을 사용자에게 준다.

- 제목은 커밋 요약과 같게 한다.
- 설명은 `CONVENTIONS.md`의 PR 양식을 채운다. 리뷰하는 사람이 혼자라 리뷰가 병목이므로, "리뷰 포인트"에는 꼭 봐야 할 곳만 짧게 적는다. 변경 파일을 그대로 나열하지 않는다.
- Unity 에디터에서 해야 확인할 수 있는 것은 "확인 방법"에 구체적으로 쓴다 (어떤 씬을 열고 무엇을 하는지).
- 환경이 PR 설명에 붙이라고 지정한 꼬리말이 있으면 붙인다.
- **병합하지 않는다.** 병합은 사용자가 한다.

### 7. 보고

한국어로 짧게 보고한다.

- 브랜치, 커밋 메시지 요약
- PR 링크 (새로 열었는지, 기존 PR을 갱신했는지)
- 변경 규모(`git diff --stat` 요약). 커지면 리뷰 부담이 되므로 숫자를 그대로 보여 준다.
- 멈췄다면 어느 단계에서 왜 멈췄는지, 사용자가 무엇을 하면 되는지
